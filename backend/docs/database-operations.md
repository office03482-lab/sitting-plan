# Database Operations Guide

## Migration commands

### Local PowerShell
```powershell
cd backend
.\venv\Scripts\python.exe -m alembic upgrade head
```

### Helper script
```powershell
.\scripts\migrate.ps1
```

### Generate a new revision
```powershell
cd backend
.\venv\Scripts\python.exe -m alembic revision --autogenerate -m "add_attendance_indexes"
```

## Rollback commands

### Roll back one revision
```powershell
cd backend
.\venv\Scripts\python.exe -m alembic downgrade -1
```

### Roll back to a named revision
```powershell
.\scripts\rollback.ps1 -Revision a6379ccf231f
```

## Existing environment baseline workflow
1. Back up the database first.
2. Inspect the live schema.
3. If it already matches the baseline, stamp it:
```powershell
cd backend
.\venv\Scripts\python.exe -m alembic stamp a6379ccf231f
```
4. From that point onward, use `upgrade head` for every future release.

## Deployment migration workflow
1. Put the app in maintenance mode if the release includes risky schema changes.
2. Take a fresh PostgreSQL backup.
3. Run:
```powershell
cd backend
.\venv\Scripts\python.exe -m alembic upgrade head
```
4. Start or restart the API.
5. Run smoke tests.

## Backup commands

### PowerShell custom-format backup
```powershell
$env:PGPASSWORD = "your-password"
.\scripts\backup_postgres.ps1 -Host localhost -Port 5432 -Database seating_planner -User postgres -OutputDir .\backups
```

### Shell backup
```bash
export PGPASSWORD='your-password'
export PGHOST=localhost
export PGPORT=5432
export PGDATABASE=seating_planner
export PGUSER=postgres
./scripts/backup_postgres.sh ./backups
```

## Restore commands

### PowerShell restore
```powershell
$env:PGPASSWORD = "your-password"
.\scripts\restore_postgres.ps1 -BackupFile .\backups\seating_planner_20260507_230000.dump -Host localhost -Port 5432 -Database seating_planner -User postgres -DropExistingObjects
```

### Shell restore
```bash
export PGPASSWORD='your-password'
export DROP_EXISTING=true
./scripts/restore_postgres.sh ./backups/seating_planner_20260507_230000.dump
```

## Automated backup examples

### Linux cron
```cron
0 2 * * * cd /opt/erp/backend && PGPASSWORD='secret' PGHOST=localhost PGPORT=5432 PGDATABASE=seating_planner PGUSER=postgres ./scripts/backup_postgres.sh /var/backups/erp
```

### Windows Task Scheduler action
```powershell
powershell.exe -File C:\path\to\backend\scripts\backup_postgres.ps1 -Host localhost -Port 5432 -Database seating_planner -User postgres -OutputDir C:\ERPBackups
```

## Retention recommendation
- Keep daily backups for `7-14` days.
- Keep weekly backups for `4-8` weeks.
- Keep monthly backups for `3-12` months depending on compliance needs.
- Store at least one copy off the app host.

## Disaster recovery notes
1. Restore to a separate validation database first when possible.
2. Verify row counts for core tables: `users`, `schools`, `students`, `teachers`, `attendance_staff`, `rooms`, `exams`.
3. Only restore in-place with `--clean` after confirming the backup is valid.
4. After restore, run `alembic current` and check app health endpoints before opening traffic.

## Migration best practices
1. Review autogenerated revisions before applying them.
2. Prefer additive changes first, destructive cleanup later.
3. Keep data migrations separate from heavy schema rewrites when possible.
4. Never rely on startup schema mutation in production.
5. Stamp legacy environments only after a full backup and schema review.
